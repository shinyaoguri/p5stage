# 0012: 外部の Gist は自分のものだけ取り込み、切り離しは配信ごと外す

## 状態

採用 (2026-08-12)

## 文脈

Phase 2-6。ここまでで「p5stage で作った作品を p5stage で編集して配る」は通ったが、
**正本の出入り**が両方向とも塞がっている。

- 既に p5.js の Gist を持っている人が、それを p5stage の作品として続けられない
- 作者が GitHub 側で Gist を消すと、その作品は保存も配信も詰む (`gist_missing` の
  409 が返り続ける)。ADR 0010 も「公開範囲を変えたいときの移し口は 2-6」と
  積み残していた

同じ時期に #44 が「作品を増やす経路」を整理し、**系譜の正典は D1 に置く**と決めた
(自分の Gist は自分で fork できないという GitHub の制約が出発点)。2-6 の口は
その整理と噛み合う位置に置く必要がある。

## 決定

### 1. 作品を増やす経路は 4 つあり、2-6 が受け持つのは 1 つ

| 経路 | GitHub 側 | 担当 |
|---|---|---|
| **外部にある自分の Gist を作品にする (adopt)** | 何もしない (その Gist をそのまま正本に) | **2-6** |
| 他人の作品を持ち込む | Gist fork API (blob 共有・`Forked from` が付く) | Phase 4 (#44) |
| 自分の作品の続きを編集 | 既存 Gist を PATCH | 2-3 |
| 自分の作品から派生を作る | 新規 Gist を作成 (自分の Gist は fork 不可) | Phase 4 (#44) |

呼び名を分ける。#44 が「取り込み」を 3 経路の総称として使うので、2-6 の口は
**adopt** と呼び、`/api/sketches/import` は将来の総称のために空けておく。

### 2. adopt できるのは自分の Gist だけ

他人の Gist を正本にすると、**書き込めない作品ができる**。書き込みは必ず本人の
トークンで行う約束なので (要件 5.2)、保存のたびに 404 か 403 が返る作品が
D1 に残ることになる。相手が中身を変えればこちらの作品も黙って変わる。

中身を複製して受け入れる案 (canvastage の取り込みはこの形) も採らない。#44 が
fork API で取りにいった `Forked from` と blob 共有 (O(1)) を捨てることになる。
他人の作品は fork と D1 の系譜で扱うのが正しく、それは Phase 4 の担当。

**持ち主が読めない Gist も断る**。匿名 Gist には `owner` が無く、そこを
「自分のもの」に倒すと所有者確認がすり抜ける。

### 3. 中身を全部読めない Gist は断る

1MB を超えるファイルは API が `truncated` で返す (要件 6)。そのまま受け入れると
配信の写しが欠けた姿で作られ、次の保存では読めなかったファイルだけが取り残される。
サービス側で 1MB 以下を強制する前提から外れた Gist は、外に置いたままの方が安全。

`index.html` が無い Gist も同じく断る (実行の起点が無い)。**受け入れるときに Gist を
書き換えて補う案は採らない** — 取り込みは相手の持ち物に触らない操作にしておく。

### 4. 公開範囲は Gist に従う

Gist は作成後に public / secret を変えられない (ADR 0010)。取り込みで選ばせると
「限定公開のつもりが Gist は公開のまま」という嘘になるので、**あちらに合わせる**。

### 5. 切り離し (detach) は配信のポインタごと外す

`gist_id` と一緒に `current_revision` / `revision_etag` / `revision_checked_at` /
`gist_deleted_at` を落とす。作品ページは「まだ保存されていません」に戻り、
次の保存で新しい Gist ができて復活する。

写しだけ配り続ける案 (R2 の中身は残っているので技術的には可能) は採らない。
**切り離したのに閲覧者から見て何も変わらないなら、切り離しの意味が無い**。
配信を続けるには「写しがどの Gist の下にあるか」を持つ列が要り、配信経路の
分岐も増える — 得るものに対して代償が大きい。

**GitHub には何もしない**。利用者の Gist は利用者のもので、こちらが消す筋合いは無い。

これは Phase 4 の「派生を作る」とは別物。派生は**新しい作品**を作る (#44 の系譜が
付く)。切り離しは**同じ作品**の正本を差し替える。

### 6. 削除に見えない言葉を使う

「切り離す」も「外す」も、消えるのだと読まれうる。操作名は「Gist を外す」とし、
確認では**削除しないことを最初の行に置く**。何が残り、何が変わるかを全部書く。

## 影響

- 取り込みは冪等。同じ Gist をもう一度渡されたら作り直さず、既にある作品を返す
  (`gist_id` は UNIQUE。同じ Gist を指す作品が 2 つあると、どちらの保存が正本に
  届くのか決まらない)
- 切り離しも冪等。既に外れていれば成功として返す (押し直しやタブの重複で失敗にしない)
- 切り離した作品の R2 の写しは孤児になる。リビジョン単位の JSON なので実害は小さい
  が、GC は Phase 3 のアセット台帳と一緒に考える
- 切り離すと `gist_id` が NULL に戻るので、**公開範囲を変えられるようになる**
  (ADR 0010 の 409 は Gist が付いている間だけ)。保存し直すと選んだ公開範囲で
  新しい Gist ができる
- `parseGistContent` が持ち主と公開範囲を読むようになった。配信の再検証でも同じ
  値が手に入るので、将来「GitHub 側で公開範囲が変わった」の検出に使える

## 補足 (2026-08-14 / #65)

**断る条件が 1 つ増えた: 自分が所有していないアセットを参照する Gist も取り込めない。**

決定 2・3 は「受け入れると**その Gist がそのまま正本になる**」を根拠に、持ち主・
truncated・ファイル構成を保存経路と同じ厳しさで見ると決めていた。`assets.json` が
その一覧から漏れていて、他人の作品から sha256 を書き写した Gist を取り込むと、
クォータを使わずにアセット付きの作品が配られていた。規則の本体と、自動で計上する案を
採らなかった理由は ADR 0003 の補足 (#65) に書いた。

判断が間違っていたのではなく、実装が決定に追いついていなかった箇所になる。検査は
取り込みの**判断の側** (`planGistAdoption`) に置き、所有の照会だけ D1 を持つ API
ルートに残した (あの関数は D1 にも GitHub にも触らない純ロジックのまま)。

**HTTP は 422** (`invalid_manifest` / `unknown_asset`)。保存経路が同じ規則に 400 を
返すのと食い違うが、これは `invalid_files` で既に採った判断と同じ — 不備があるのは
要求の本文ではなく**外部の資源**で、こちらの本文 (`{ gist: ... }`) は正しい。

**取り込みの冪等性は、マニフェストが今も自分の所有で成り立っている間だけ**。同じ Gist を
二度渡せば既にある作品を返すが、その間にアセットを手放していれば 422 になる
(再取り込みも `publishRevision` まで進む経路なので、検査は既取り込みの分岐より前に置いた)。
