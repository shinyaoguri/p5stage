# 0016: リビジョン履歴は「写しを持っている版」の台帳で、主体は作品ではなく Gist

## 状態

採用 (2026-08-15)

## 文脈

要件 3.2 は「過去リビジョンの閲覧: マニフェストごと解決するため当時のアセットで再現できる」を
挙げ、ADR 0011 は「作品ページがリビジョン単位の URL を持てる下地ができた。履歴の閲覧 UI
(Phase 4) はキーを差し替えるだけで載る」と書いた。R2 の写しは
`gists/<gistId>/<revision>.json` の不変オブジェクトで、`getRevision` は最初から任意の版を
引ける。Phase 3 も「旧リビジョンを画面から描き直す確認は Phase 4」と積み残している (#48)。

足りないのは **どの版が存在するかを列挙する手段**だけ。それを足すにあたって決めることが
4 つある。

1. **台帳の主体を何にするか。** 作品 (`sketch_id`) か、写しのキーと同じ Gist (`gist_id`) か
2. **どこで記録するか。** 中身を R2 へ書く `storeRevision` か、配信するポインタを進める
   `setCurrentRevision` か
3. **写しが無い版をどう扱うか。** 今の配信は写しが無ければ GitHub から取って埋める
4. **何を「履歴」と呼ぶか。** Gist の本当の履歴と、こちらが写しを持っている版は一致しない

## 決定

### 台帳の主体は Gist (`gist_revisions(gist_id, revision, created_at)`)

配られる実体と同じ単位で数える。これは `blob_refs` が
「参照の主体は作品ではなく、**R2 にあるリビジョンスナップショット**」を選んだのと同じ理由で、
2 つの表は `(gist_id, revision)` で並ぶ兄弟になる (`blob_refs` は「アセットを参照する版」だけの
部分集合で、`gist_revisions` がその全体を持つ)。

作品を主体にすると、**切り離し (detach) が効かなくなる**。`detachGist` は `gist_id` と
`current_revision` を同時に落とし、作品ページは「まだ保存されていません」に戻る
(ADR 0012 は「切り離したのに閲覧者から見て何も変わらないなら、切り離しの意味が無い」と
決めた) が、R2 の写しはそのまま残る。作品を鍵に履歴を残すと、`?rev=` から旧 Gist の中身を
配り続ける裏口が 1 本開く。Gist を鍵にすれば、`gist_id` が NULL になった時点で履歴も
自然に空になる。

取り込み (adopt) も同じ形で収まる。GitHub の Gist は所有者を移せないので、`gist_id` で
引いた履歴が別人のものになる経路が無い。

### 記録は `storeRevision` — 写しを書いた場所と同じ

台帳が意味するのは「**配れるスナップショットがある**」ことなので、それを保証している関数と
同じ場所に置く。`storeRevision` は R2 へ書いた直後に `recordRefs` を呼んでおり、履歴も
同じ地点に並ぶ。

配信のポインタを進める `setCurrentRevision` に混ぜる案は採らない。

- 不変条件の持ち主が違う。「写しがある」は `storeRevision` が守っていて、ポインタの前進は
  その後の別の話 (`publishRevision` は前者に失敗したら後者に進まない)
- `store.ts` は作品メタデータの D1 層。次の縦切り (Durable Objects + SSE) は「版が進んだ」を
  通知する地点を必要とするが、それを `store.ts` に置くと D1 の層が DO のバインディングに
  依存し始める

### 過去の版のために GitHub へは取りに行かない

今の `resolveSketchContent` は写しが無ければ `fill` に落ち、GitHub から**今の Gist**を
取って埋める。これを `?rev=` に流用すると 2 つ壊れる。

- 写しが失われた版を開いたとき、**最新の中身が「その版」として閲覧者に出る**
- 存在しない版を並べた要求 1 回につき GitHub API を 1 回叩く。閲覧経路から GitHub を
  外した ADR 0011 が、URL のクエリ 1 つで無効化される

そこで過去の版の解決は**別の関数** (`resolveRevisionContent`) に分け、(1) 台帳に無ければ
断る、(2) 写しが無ければ「この版は残っていません」と言う、(3) GitHub を叩かず、ポインタも
書き換えない、を実装で固定する。既存関数への引数追加で済ませない — `fill` への分岐が
奥に残る形にしない。

過去の版を見ている間は再検証 (`revalidate`) も走らせない。最新を確かめ直す理由が無く、
走らせれば GitHub の消費がまた閲覧数に比例し始める。

### 「履歴」= p5stage が写しを持っている版

Gist の本当の履歴とは一致しない。ずれるのは 2 か所。

- 作者が gist.github.com で直接編集した場合。こちらが気付くのは再検証のときなので
  (既定 10 分)、その間に複数回コミットされると中間が抜ける
- 取り込み (adopt) した Gist の、取り込む前の版

GitHub の `history` 配列を保存すれば一覧は本当の履歴に近づくが、**中身を配れない行が並ぶ**
(配るには閲覧のたびに `GET /gists/:id/:sha` を叩くことになり、ADR 0011 に反する)。
一覧に出す以上は開けるべきなので、**持っている版だけを、そう名乗って出す**。

同じ理由で `created_at` は「p5stage が写しを持った時刻」であって、GitHub のコミット時刻では
ない。画面の文言もそう書く。

### キャッシュは「不変なもの」だけを不変にする

不変なのは R2 のオブジェクトであって、**ページの HTML ではない**。作品ページにはタイトル・
説明・作者の login とアバターが入るので、過去の版のページに長い `s-maxage` を付けると、
作品名を直しても古い名前のまま何日も残る (purge の口は無い)。

- ページ HTML は今のまま (公開は `s-maxage=60`、限定公開は `private, no-store`)
- 過去の版のページは `noindex`。canonical は今までどおりクエリの無い正典 URL を指す
  (公開作品の版が増えるほど、検索エンジンに近似重複を見せることになる)
- 中身だけを不変のまま配る口 (JSON) は、必要になる次の縦切り (SSE で受けた版に画面を
  差し替える) で作る。アセットの配信 (`/a/<sha256>/<name>` — ADR 0014) が既に
  `immutable` を付けているので、形はそれに倣う

## 影響

- 台帳は 4-1 以降に `storeRevision` を通った版しか知らない。既存分は R2 の `gists/` を
  舐めて埋める (`revision-backfill.ts`)。参照台帳のバックフィル (ADR 0015) と同じ形だが、
  **キーだけで組を作れるので中身は読まない**。続きの位置は `gc_state` の別のキーに持つ
  (参照台帳側は「済み」になると二度と走らないため、相乗りできない)
- 作品ページに `?rev=<sha>` が増えた。正典 URL への 302 (`/s/:id` と login の付け替え) は
  この値を引き継ぐ。今配信している版を指す `?rev=` は、クエリの無い URL へ寄せる
- **並び順は「写した時刻」なので、埋め直しが入ると前後しうる**。R2 の `uploaded` は
  写しを書いた時刻であって、その版が作られた順ではない (閲覧時の埋め合わせで古い版が
  後から書かれることがある)。今の版が必ず先頭に来るとは限らないので、一覧では
  **今の版に印を付けて**位置に頼らない形にした
- 履歴は実行のたびに伸びる (debounce 保存 → 版)。行そのものは軽く、R2 の写しは以前から
  同じ勢いで増えているので、**先に困るのは表示**。一覧は件数を絞って出す。保持期間は
  設けない — 行を消しても写しは残り、`blob_refs` は回収の安全のため消せない (ADR 0015) ので、
  「履歴から消える」「配信が止まる」「実体が回収される」を揃えないと中途半端になる
- #70 (GitHub 側で書き換えられた `assets.json` を再検証が素通しする) が作る版にも、
  履歴という恒久的な入口ができる。露出が増えることを Issue に書き足した
