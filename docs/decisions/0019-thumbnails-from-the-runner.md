# 0019: サムネイルは実行環境で撮り、版ごとに不変な 1 枚として配る

## 状態

採用 (2026-08-15)

## 文脈

要件 3.4 は「サムネイル: 実行キャンバスから自動取得 → R2 保存、Cloudflare Images で
リサイズ配信」。移植元の canvastage に相当実装は無く、**別オリジンの iframe から
画素を持ち帰る**ところを新しく作ることになる (ADR 0007)。

制約は 3 つある。

- **本体は canvas を読めない。** スケッチはランナー (preview オリジン) の中の
  入れ子 iframe で動く。読めるのはランナーだけで、本体との間は postMessage しかない
- **プロトコルの版が上がる。** メッセージを足すので `PROTOCOL_VERSION` は 2 → 3。
  本体とランナーは別々にデプロイされる (ADR 0007 の補足 / Phase 4-4a)
- **撮れないスケッチがある。** canvas を作らないもの、外部の画像を CORS 無しで
  読み込んで汚染された canvas。どれも作品としては正常に動いている

## 決定

### 1. 撮るのは実行環境、頼むのは本体 — 版 3 の 2 メッセージ

`capture` (本体 → ランナー) と `thumbnail` (ランナー → 本体) を足す。運ぶのは PNG の
`Blob` で、本体は画素に触れない。**撮れなかったことも必ず答える** — 黙って返事を
しないと、本体からは「サムネイルを知らない古いランナー」と区別が付かない。

受け取った `Blob` は `parseRunnerMessage` が形式 (`image/png`) と大きさ (512KB) で
確かめる。送り主はオリジンと送信元を検証した相手だが、**そこで動いているのは他者の
コードが触れる文書**なので、信頼境界の作法どおり中身を見る。

### 2. 撮るのは作者のエディタだけ、保存が着地した瞬間に 1 回

実行 → 間引き保存 → 着地の順なので、そのとき画面に出ているのは保存された中身そのもの。
作品ページ (閲覧者側) は撮らない — **他人の実行結果が作者の作品の顔になる経路を
作らない**。

失敗は黙って捨てる。飾りなので、撮れないスケッチのために編集を妨げる知らせを出す
価値が無い。次の保存でまた試す。

### 3. 鍵は (gist, リビジョン)。版ごとに不変

R2 の `thumbs/<gistId>/<revision>.png` に置く。リビジョンの写し
`gists/<gistId>/<revision>.json` (ADR 0011) の兄弟キーで、**書いた絵は二度と
変わらないので無効化の仕組みが要らない**。過去の版の絵もそのまま残る。

置き場は配信用のバケット (`CONTENT`)。アセット (`BLOBS`) は正本で、失うと作品が
壊れるが、サムネイルは次の保存で撮り直せる。寿命が違うものを同じ GC に載せない
(ADR 0003 と同じ理由)。

D1 に持つのは `sketches.thumbnail_revision` の 1 列だけ。**`current_revision` とは
別に持つ** — 撮影は保存に必ず追いつくとは限らないので、最後に撮れた版を指したままに
なる (何も出さないより、少し古い絵の方が役に立つ)。Gist が外れると R2 のキーごと
意味を失うので、`detachGist` が一緒に NULL へ戻す。

### 4. クォータには載せない

`user_blobs` の計上規則は「持ち込んだ時点で計上」(ADR 0003) だが、サムネイルは
利用者が持ち込んだ素材ではなく、保存に付いてこちらが作らせた派生物。数えると
「作品を保存するほど自分の枠が減る」ことになり、規則の意味が変わる。

代わりに上限で守る: 作者だけが・配信中の版にだけ・PNG を・512KB まで。
撮る側が長辺 1200px へ縮めてから送るので、通常はこれに遠く及ばない。

### 5. 配信は assets オリジンの `/t/`

中身は他者のコードが描いた画素なので、アセット (`/a/`) と同じ扱いにする — 本体の
オリジンから利用者由来のバイト列を配らない (ADR 0014)。ヘッダも同じ作法
(`immutable` / `nosniff` / CORP / CSP / `Access-Control-Allow-Origin: *`)。

### 6. Cloudflare Images は使わない — 撮る側で 1 枚に正規化する

要件は「Cloudflare Images でリサイズ配信」と書いているが、**今要るサイズは 1 つだけ**
(作品ページの OGP)。変換を挟むと課金 (無料枠 5,000 変換/月) とゾーン設定が増え、
得られるものが無い。ランナーが長辺 1200px に縮めた PNG を 1 枚だけ作る。

複数サイズが要るのは作品一覧の器ができる Phase 5。そのとき、**元の 1 枚は既に
R2 にある**ので、変換を足す判断はそこで改めて行える (要件 3.4 はこの方針に改訂した)。

### 7. カードを出すのは最新の版だけ。限定公開でも出す

`og:image` を出すのは最新の版を見ているときだけ。過去の版のページは `noindex` で
近似重複を並べない方針 (ADR 0016) なので、カードも作らない。

限定公開 (`unlisted`) でも出す。「URL を知る人は見られる」ものを共有した先で
カードが出るのは本来の用途で、画像の鍵は gist の ID とリビジョン SHA なので推測できない。
ページ自体は今までどおり `noindex` / `private, no-store` のまま。

**系譜の親リンク (ADR 0018 の決定 9) と扱いが違う**のは、あちらが「子を見た人に
親の URL を配る」— つまり URL を知らない第三者へ届く経路だったのに対し、こちらは
**自分の作品の URL を自分で共有したとき**にしか使われないため。

## 影響

- `PROTOCOL_VERSION` が 3 になる。Phase 4-4a で本体が範囲で受けるようにしたので、
  ランナーが先に出ても本体が先に出ても実行は止まらない (ADR 0007 の補足)
- 保存のたびに PNG が 1 枚増える。R2 のオブジェクト数はリビジョンの写しと同じ
  伸び方で、消す仕組みはまだ無い (孤児 blob の回収 — ADR 0015 — はアセット専用)。
  リビジョンの写しごと掃除する話になったときに一緒に扱う
- 作品一覧 (Phase 5) は `thumbnail_revision` と `thumbnailPath()` をそのまま使える。
  **限定公開の作品を一覧に出さない**規則は ADR 0018 の申し送りと同じ
- WebGL の canvas が読めるのは p5 が `preserveDrawingBuffer: true` で
  コンテキストを作っているため。この前提は `e2e/thumbnail.spec.ts` が実物で押さえる
