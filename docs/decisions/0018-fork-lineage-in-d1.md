# 0018: フォークの系譜は D1 に持ち、GitHub の `Forked from` はボーナスとして扱う

## 状態

採用 (2026-08-15)

## 文脈

Phase 4-3。ここまでで p5stage には**他人の作品に触る道が無い**。閲覧はできるが、
そこから自分の作品を始められない。

作品を増やす経路は ADR 0012 が 4 つに整理し、実装済みは 2 つ (既存 Gist の続きを
編集 / 外部にある自分の Gist の取り込み)。残る 2 つ — **他人の作品を持ち込む**と
**自分の作品から派生を作る** — がこの縦切りの担当になる。

出発点は GitHub の制約 (#44)。**自分の Gist を自分で fork することはできない**
(`POST /gists/{id}/forks` は 422 `You cannot fork your own gist.`)。しかも fork で
GitHub に残るのは Gist 同士の関係だけで、p5stage の作品同士の系譜はそこからは引けない。

この ADR は 4-3a (他人の作品をフォークする) で決めたことを残す。自分の作品から
派生を作る経路は 4-3b で、判断はここに揃えてある (口も純ロジックも共通)。

## 決定

### 1. 系譜の正典は D1。GitHub の `Forked from` はボーナス

`sketches` に `forked_from_sketch_id` / `forked_from_revision` を持つ。経路によって
GitHub 側にリンクが付いたり付かなかったりするので、**閲覧体験を GitHub に依存させない**。
作品ページの「〜から派生」は常に D1 由来で出る。

### 2. 口は 1 つ、分岐はサーバが Gist の持ち主で決める

`POST /api/sketches/:id/fork` の 1 本にして、クライアントは経路を意識しない。

**分岐は `content.ownerId === viewerId`** — GitHub から読んだ Gist の持ち主で取る。
D1 の `sketches.owner_id` ではない。回避したい制約は GitHub 側のもの (自分の Gist は
fork 不可) であって、D1 の所有ではないため。両者がずれたとき、D1 で分けると 422 が
そのまま利用者に出るが、Gist で分ければ構造的に起きない。持ち主が読めない Gist (匿名)
は「自分ではない」に倒す。

`/api/sketches/import` は総称のために空けたままにする (ADR 0012 の決定 1)。

### 3. GitHub に何かを作る前に、親の Gist を 1 回読む

検証もクォータの判定もその手前で済ませる。断るときに**利用者のアカウントへ
フォーク済みの Gist を残さない** (`adopt.ts` が「分岐の前なら D1 へ 1 行も書かずに
断れる」と置いたのと同じ考えを、GitHub 側にも適用する)。

読んだ版の SHA がそのまま `forked_from_revision` になる。`sketches.current_revision`
を代用しないのは、作者が GitHub 側で直接編集していたときに**実際に複製した版とは
違う SHA を刻む**ため (ADR 0016 が「履歴は p5stage が写しを持っている版」と書いた
のと同じずれ)。

### 4. `forkGist` は新しい Gist の ID しか返さない

`POST /gists/{id}/forks` の 201 は読み出しと**同じ形ではない**。GitHub のスキーマ上
そこに `history` は無く、`files` にも `content` が入らない。`parseGistRevision` を
当てれば「応答が想定と違う形」で落ち、`parseGistContent` を当てれば全ファイルが
truncated に見える。

そこで `parseGistId` を足して **ID だけ**を受け取り、中身と版は新しい ID で
`fetchGist` を 1 回叩いて取り直す。偽 GitHub の fork 応答も同じく `history` と
`content` を抜いてある — ここを GET と同じ本文にすると、**E2E は通るのに本番だけが
落ちる**経路ができる。

### 5. 複製されるのは GitHub 上の今の版

fork API は版を選べない。過去の版 (`?rev=`) を見ている閲覧者にはボタンを出さない —
押した結果が見ているものと違うのは裏切りになる。

### 6. アセットは実体があるものだけ引き受け、無ければ断る

フォークは**他人の blob を自分に計上する**唯一の経路になる (ADR 0003 の補足が
「フォークで他人の blob を持ち込む場合もここに行が増える形にすれば、計上の規則は
1 つで済む」と Phase 4 に預けたもの)。

- 台帳 (`blobs`) に実体が無い sha256 を含む作品は**フォークさせない**。放置すると
  「次の保存が必ず 400 になる、利用者には直せない作品」ができる。adopt が同じ状態を
  断っているので、規則を 1 つに保つ
- 既に自分が持っている分はクォータの合計から除く。除かないと、同じ素材を使う作品を
  2 つフォークしただけで 2 回請求され、`user_blobs` の主キーで 1 行しか増えない実態と
  食い違う
- **計上は作品の行を作るより先**。途中で落ちたときに残るのが「余計に計上された blob」
  (3-4b の手放しで戻せる) か「所有していないアセットを参照する保存できない作品」
  (利用者には直せない) かの違いになる

**R2 に実体があるかまでは確かめない。** 回収は R2 → D1 の順で消す (ADR 0015) ので
「台帳にあるが実体が無い」窓は開くが、そのとき元の作品も同じ状態で、フォークが
新しく壊すわけではない。claim (`POST /api/assets`) が `blobExists` で裏を取っているのは
**転送を省く判断**のためで、こちらは省く転送が無い。

### 7. 公開範囲は、できた Gist に従う

fork は元が secret なら secret になり (公開範囲の意図しない昇格は起きない — #44)、
こちらから選べない (ADR 0010)。ただし**利用者が選ばないまま自分の名前で公開された
作品が 1 件増える**ので、確認ダイアログに「元の公開範囲を引き継ぎます (GitHub の
制約で選べません)」と、どちらになるかを明記する。`normalizeVisibility` が
「公開は明示的な選択でなければならない」と決めている以上、黙って進めない。

タイトルと説明は**親の D1 行から引き継ぐ**。Gist の description から復元しない
(adopt がそうしているのは、外の Gist に D1 の行が無いからで、フォークにその制約は無い)。

### 8. 冪等にしない

「1 つの作品から 2 つの派生を作る」は正当な使い方で、adopt のような構造的な衝突
(`gist_id` の UNIQUE で正本が決まらない) も無い。二度押しは**確認ダイアログの
送信中無効化**で塞ぐ。

ただし GitHub が再 fork で既存の Gist を返す可能性に備え、`gist_id` の UNIQUE 違反は
`adopt.ts` と同じ回復パターン (引き直して自分のものなら 200 で返す) を置く。
どちらの挙動でも壊れない。

### 9. 系譜のリンクは親が `public` のときだけ

限定公開の親を持つ公開の子に親の URL を出すと、`s-maxage=60` のエッジ越しに
**その URL を知らない全員へ配られる**。`unlisted` は「URL を知る人は見られる」=
**URL が防御そのもの**なので (要件 3.4)、ここで漏らすと「fork しても公開範囲の
意図しない昇格は起きない」という #44 の前提が崩れる。

親が公開でなければ「限定公開の作品から派生」とだけ出す。親の存在自体は子から
辿れる事実なので隠さないが、URL は出さない。

### 10. 購読と同じく、見られる人はフォークできる

限定公開の作品もフォークできる。`getSketch` が「ID を知っていることが閲覧の条件
そのもの」と決めており (要件 3.4)、ADR 0017 も購読の入口を同じ強度に置いた。実際、
secret gist は ID を知っていれば GitHub 上で直接 fork できるので、こちらで塞いでも
意味が無い。

**フォークされた時点で元の作者は取り消せない**。これは GitHub の fork と同じ性質で、
限定公開は「非公開ではない」という要件 3.4 の言い換えでもある。

## 影響

- 作品を消す口はまだ無いので、`forked_from_sketch_id` に外部キーを張ったままにできる。
  消せるようになったときに「親を消したら子の系譜はどうなるか」を決める必要がある
- **子 (派生) の一覧は Phase 5 へ送る**。作品一覧の器が要る。決定 9 の規則はそこでも
  必要になる (子が `unlisted` なら親のページに出さない)
- 種の E2E に「偽 GitHub にも実体がある作品」が初めて登場した。他の種は GitHub 側に
  無いことを前提にしたテストがあるので、フォーク専用に分けてある
- `POST /api/assets` が「sha256 を知っていれば他人の blob を計上できる」形なのは
  変わらない (dedup の必然)。フォークはそこに**出所のある経路**を足したことになる
