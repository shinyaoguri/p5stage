# 0015: 孤児 blob は自前の Worker エントリに載せた Cron が、印と猶予を経て回収する

## 状態

採用 (2026-08-14)

## 文脈

ADR 0003 は「孤児 blob の GC は参照カウント + 猶予期間で、**公開済みリビジョンが参照する
blob は原則削除しない**」と書いたが、Phase 3-5a まででできたのは台帳だけだった。
実体を消す経路が無いので、**誰にも計上されず誰にも参照されていない実体が R2 に
永久に残る**。所有を手放しても (`DELETE /api/assets/<sha256>`) 消えるのは
`user_blobs` の 1 行だけで、R2 も `blobs` もそのまま。

回収を作るにあたって決めるべきことが 4 つある。

1. **どこで走らせるか。** Astro の Cloudflare アダプタが生成するエントリは `fetch` しか
   持たない。Cron (`scheduled`) は HTTP の経路を持たないので、そこには現れない
2. **何を孤児と呼ぶか。** 所有と参照は別の表にあり (ADR 0003 の補足)、参照は「今配信して
   いる断面」と「全期間」の 2 通りに読める
3. **猶予をいつから数えるか。** `blobs.created_at` から数えると、上げた直後の
   (まだどのリビジョンからも参照されていない) blob が消える
4. **既にあるリビジョンをどうするか。** 参照台帳は 3-5a 以降に `storeRevision` を通った
   分しか知らない

## 決定

### Cron は自前の Worker エントリ (`apps/web/src/worker.ts`) に載せる

`wrangler.jsonc` の `main` を自前のファイルにして、アダプタのエントリを包む。
`fetch` はそのまま委譲し、足すのは `scheduled` だけ。

```ts
import astroEntry from "@astrojs/cloudflare/entrypoints/server";
export default {
  fetch: astroEntry.fetch,
  async scheduled() { await runAssetGc(Date.now()); },
} satisfies ExportedHandler<Env>;
```

- **Cron 専用の 2 つ目の Worker は作らない。** D1 も R2 も本体に既にあり、回収のコードは
  本体の台帳 (`lib/assets/store.ts`) をそのまま使う。デプロイ単位を増やすと、同じ表を
  読む場所が 2 つに分かれる
- **HTTP の口を開けて外から起こす形も採らない。** 判断の材料は全部サーバ側にあり、
  利用者が起こす理由が無い。秘密を持たせて守るくらいなら、口を作らない方が短い

これは `wrangler.jsonc` が「Durable Objects を足す Phase 4 で差し替える」と書いていた
分の前倒しで、Phase 4 の DO もここに載る。

### 孤児 = 所有が無く、**全期間**のどのリビジョンからも参照されていない blob

起点は必ず `blobs` の行。実体の無い sha256 を指す `blob_refs` の行 (利用者が手で書いた
マニフェスト — 3-5a) は、`blobs` を起点に引く限り出てこないので放っておいてよい。

参照を全期間で見るのは、**過去のリビジョンが R2 に残り、いつでも配りうる**ため
(ADR 0011 の配信経路は D1 のポインタ → R2 の不変オブジェクト)。作品ページの履歴から
過去リビジョンを引けば、当時のアセットがそのまま要る — それが ADR 0003 の
「リビジョン = コード + アセットの完全なスナップショット」の意味。

手放し (`DELETE /api/assets/<sha256>`) が今の断面しか見ないのと**逆向き**になるが、
矛盾ではない。同じ台帳を 2 つの読み方で使う (3-5a の補足)。

| 用途 | 読む範囲 | 守りたいもの |
|---|---|---|
| 手放し | 今配信しているリビジョン | 次の保存が `unknown_asset` で断られないこと |
| 回収 | 全期間 | 配られうる実体が消えないこと |

### 猶予は「孤児と気付いた時刻」から数える (`blobs.orphaned_at`)

回収は 2 相に分かれる。

- **印 (mark)**: 孤児を見つけたら `orphaned_at` に今を書く。既に印があるものは触らない
  (触ると猶予が毎回振り出しに戻り、いつまでも回収されない)
- **回収 (sweep)**: 印から猶予 (既定 7 日 — `ASSET_GC_GRACE_HOURS`) を過ぎたものだけ消す

`created_at` から数えないのは、**上げた直後の blob が孤児ではない**から。持ち込んだ
時点で所有に計上される (3-1) ので、孤児になるのは最後の所有者が手放した瞬間であり、
その時刻はどの列にも無い。印を置いて初めて数えられる。

猶予の間に所有か参照が戻ったら印を消す (復活)。回収より先に必ず通す。

### 消す順は R2 → D1

逆にすると台帳から行が消えて実体だけが残り、回収は `blobs` を起点に引くので**二度と
見つけられない**。この順なら、途中で失敗しても「台帳にあるのに実体が無い」で止まり、
`blobs` の行が残っているので次の起動がやり直せる。

その代わり「台帳にあるのに実体が無い」窓ができる。ここで claim (`POST /api/assets`) が
dedup して `stored` と答えると、転送を省いた結果**中身だけ存在しないアセット**を持つ
作品ができる。**claim は台帳で見つけた blob の実体を R2 に確かめてから**転送を省く。
`orphaned_at` の有無では判断しない — 印が付いていても実体はまだあり、そこで転送させると
猶予の間の持ち直しが無駄に高くつく。

### 回収を始める前に、R2 のリビジョンから参照台帳を埋める

参照台帳は 3-5a 以降に `storeRevision` を通った分しか知らない。埋めずに回収を回すと、
**既存の作品が使っている実体を全部孤児と見なす**。R2 (`CONTENT`) の `gists/` を舐め、
キー (`gists/{gistId}/{revision}.json`) と中身のマニフェストから、書いた当時と同じ記録を
作り直す。同じ組を二度書いても行は増えない (`recordRefs`)。

1 回の起動で舐め切らないので、続きの位置は D1 (`gc_state`) に持ち越す。**舐め終える
までは印も回収も動かさない。**

## 影響

- 実体が消える経路ができた。消したものは戻せないので、回収の結果は毎回ログに残す
  (何をどれだけ消したか — `asset-gc {...}`)
- 猶予はユーザーごとではなく全体の設定値 (`ASSET_GC_GRACE_HOURS`)。有料プランで
  クォータを変える (要件 3.3) 話とは別の軸に置いてある
- E2E は `wrangler dev --test-scheduled` が開く `/__scheduled` から起こす。この口は
  wrangler が**バンドル時に**差し込むため、アダプタの出力が持つ「バンドル済み」の印
  (`no_bundle`) を E2E 用に落としている (`e2e/prepare-dev-worker.ts`)。本番の
  デプロイはアダプタの出力そのまま
- 台帳と実体がずれるのは「台帳にあるのに実体が無い」側だけになった。逆 (実体があるのに
  台帳に無い) は回収が拾えないまま R2 に残るが、アップロードは R2 → D1 の順で書く
  (3-1) ので、そちらが生まれるのは書き込みが途中で切れたときに限られる
