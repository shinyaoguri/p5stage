# 0004: フロントエンドを Astro + islands で構成する

## 状態

採用 (2026-08-11)

## 文脈

ADR 0001 で保留していたフロントエンドフレームワークの選定。p5stage の画面は性質が
はっきり二分される。

- **エディタ**: 透過 Monaco が実行キャンバスに重なる 1 枚の重いアプリ。移植元の
  canvastage は素の DOM + TypeScript で 5,776 行 (28 ファイル) の実装を持ち、
  ルーティングは 1 つも無い。フレームワークの恩恵が薄く、Monaco 自体が命令的な API
- **発見系のページ群**: ギャラリー・作品ページ・ユーザーページ・検索 (要件 3.5)。
  v1 のスコープに入っており、ログイン不要で閲覧される = 検索エンジンと OGP が効く。
  D1 から引いたメタデータを初期 HTML に載せたい

素の DOM を続けるとページ群のルーティング・一覧 UI・OGP をすべて自前で書くことになり、
canvastage にその実績は無い。逆に全体を SPA にするとエディタのために発見系ページまで
クライアント描画になり、初期表示と OGP を別途作り込む必要が出る。

## 決定

Astro (SSR + islands) を採用する。

- 発見系ページは Astro の MPA として描画する。既定を `output: "server"` とし、
  D1 を引かないページ側に `export const prerender = true` を置く
- エディタは `client:only` の island として載せ、canvastage の素の DOM 実装を
  ほぼ無変換で移植する。island の中では従来どおり命令的に書く
  (→ **実装は Astro ページ内の `<script>` になった。`client:only` は UI フレームワークの
  コンポーネントに付けるディレクティブで、下の「UI フレームワークは入れない」と両立しない。
  素の DOM を命令的に書くという趣旨は `<script>` のまま満たせている**)
- UI フレームワーク (React 等) は入れない。必要になった時点で island 単位で導入できる

## 影響

- 発見系ページの SEO / OGP / 初期表示が構造で担保され、専用の作り込みが要らない
- canvastage からの移植コストが最小に保たれる (island の中は素の DOM のまま)
- Astro 固有の構文とビルドの学習が必要になる。ESLint / Prettier も Astro 用プラグインを足す
- ページ間の状態共有は URL とサーバ側に寄る。エディタの状態を他ページへ持ち回る設計は取れない
  (要件上そのような画面遷移は無い)
