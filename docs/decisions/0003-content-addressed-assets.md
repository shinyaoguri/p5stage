# 0003: アセットは content-addressed blob + Gist 内マニフェストで管理する

## 状態

採用 (2026-08-11)

## 文脈

画像・3D モデル等のアップロード (OpenProcessing 同等の自由度) が要件だが、Gist API は
テキスト専用でバイナリを扱えない。最も近い実績である p5.js Web Editor は
「S3 に可変な名前付きファイル + バージョン管理無し」で、アセットを差し替えると過去の
見た目が再現不能になる構造的欠陥を抱える (アセット台帳を持たず S3 実測でクォータ計算する
ズレ、削除と参照の非同期による破損も既知問題)。Glitch (CDN + マニフェストファイル) と
Observable (バージョン付き添付) が、この問題を構造で解いた先例。

## 決定

- アセット実体は R2 に **sha256 をキーとする不変 blob** として保存する
- Gist 内の **assets.json** (ファイル名 → sha256 / size / mime) で参照する。
  マニフェストが Gist リビジョンに含まれるため、**リビジョン = コード + アセットの
  完全なスナップショット**になり、過去リビジョンは当時のアセットで再現される
- コード内は相対ファイル名のまま (`loadImage("cat.png")`)。実行 iframe への注入時に
  マニフェストで blob URL へ解決する (canvastage buildHtml() の拡張)
- fork は Gist fork (コード + マニフェスト複製) のみで blob は共有 (O(1)、dedup)。
  クォータは参照 blob の合計サイズを各ユーザーに満額計上する
- アップロードは Worker 経由で sha256 / MIME / クォータを検証。クライアントが先に
  sha256 を計算し、既存 blob なら転送をスキップする
- 配信は R2 + カスタムドメイン (本体と別オリジン)、`Cache-Control: immutable`、nosniff
- 台帳は D1 を正本とする (blobs / 参照テーブル)。GC は参照カウント + 猶予期間で、
  **公開済みリビジョンが参照する blob は原則削除しない**
- 形式は allowlist (画像 png/jpg/gif/webp・3D obj/gltf/glb・音声 mp3/wav/ogg・
  データ json/csv/txt・フォント otf/ttf)。SVG / HTML は XSS ベクタのため初期除外。
  クォータ初期値は 1 ファイル 5MB / ユーザー合計 250MB (ユーザー単位の設定値として持ち、
  有料プランで引き上げ可能な構造にする)

## 影響

- 準リアルタイム同期・リビジョン再生・フォークがすべて「不変 blob + マニフェスト」の
  上に単純に載る
- 孤児 blob の GC と参照カウント管理という運用責務を負う (台帳を D1 正本にすることで
  p5.js Web Editor の実測ズレ問題を回避)
- blob は複数作品から共有されるため、テイクダウンが blob 単位で全参照作品へ波及する。
  規約に明記する
- ユーザーが Gist 側で assets.json を直接壊せる。読み込み時のスキーマ検証 (zod) と
  エラー表示を実装で必須とする

## 補足 (2026-08-13 / Phase 3-1)

**クォータの計上は「参照」ではなく「所有」で数える。** 上の決定は「参照 blob の合計
サイズを各ユーザーに満額計上する」と書いているが、アップロードした直後の blob はまだ
どのリビジョンからも参照されていない。参照だけを数えると「参照しないまま上げ続ける」が
無料になり、クォータが上限として働かない。

そこで台帳に `user_blobs` (利用者 × blob) を置き、**持ち込んだ時点で計上する**。
フォークで他人の blob を持ち込む場合 (Phase 4) もここに行が増える形にすれば、
「満額計上する」という元の意図はそのまま保たれ、計上の規則は 1 つで済む。

参照 (どのリビジョンがどの blob を使っているか) は GC のために別途要る。それは
マニフェストから導出するもので、クォータの計上単位とは別の表になる (3-5)。

## 補足 (2026-08-14 / Phase 3-2)

マニフェスト (`assets.json`) を実装するにあたって決めたこと。

**検証は zod ではなく手書きにした。** 上の決定は「スキーマ検証 (zod)」と書いているが、
対象はファイル名 → 3 項目のフラットな表 1 つで、手書きでも 60 行程度に収まる。既存の
検証 (`fileNameError` / `parseSketchFiles` / `parseAssetClaim`) はすべて手書きで、
**「なぜ駄目か」をそのまま利用者に見せる日本語**を返す形に揃っている。zod を入れても
そのメッセージ対応表は結局書くことになり、検証の書き方だけが 2 通りになる。マニフェストは
実行時の解決 (3-3) と管理 UI (3-4) でブラウザ側も読むため、この規模の検証のために
runtime dep を足したくないという事情もある。置き場は `packages/shared/src/asset-manifest.ts`
1 つなので、必要になれば差し替えられる。

**`assets.json` は予約名として扱う。** 利用者が同名のデータファイルを持ち込む可能性は
あるが、そのときは名前を変えてもらう。中身の形で「マニフェストか利用者のデータか」を
推測する道は採らない — 壊れたマニフェストを黙って利用者のデータと解釈することになり、
アセットが理由も無く消えたように見える。エディタは改名と新規作成を断り、中身の編集と
削除は許す (壊れたものを直す手段は残す)。

**マニフェストは version を持つ。** 利用者の Gist に残り続けるファイルなので、
知らない版は**読めるふりをせずに断る**。読み飛ばすと、解釈できなかったアセットを
次の保存で消してしまう。

**entry の mime はファイル名の拡張子と一致しなくてよい。** mime はアップロード時に
中身から決まった値 (3-1 の署名検査を通ったもの) で、`.png` に改名した jpeg は
jpeg として配る方が正しい。

**参照できるのは自分が所有している blob だけ。** sha256 を書くだけで他人の blob を
参照できると、クォータを一切使わずにアセットを持つ作品が作れてしまい、「所有で数える」
(上の補足) が上限として働かない。保存経路で `user_blobs` に照会して断る。他人の
アセットを持ち込む道はフォーク (Phase 4) で、そこでは同じ表に行が増える。

## 補足 (2026-08-14 / Phase 3-3)

**「実行 iframe への注入時に blob URL へ解決する」は ADR 0014 で差し替えた。**
上の決定は実行 iframe を別オリジンに置く前 (ADR 0007 より前) の記述で、本体が
持っている中身を iframe へ渡す形しか想定していない。実際には配信オリジンの URL を
そのまま参照する方が、大きいアセットをメモリに載せず、`Range` も `immutable` の
キャッシュも効く。配信オリジンの作り方と合わせて ADR 0014 に書いた。

## 補足 (2026-08-14 / Phase 3-4b)

**所有を手放しても blob と R2 の実体は消さない。** `DELETE /api/assets/<sha256>` が
消すのは `user_blobs` の 1 行だけで、クォータの計上から外れるところまでを受け持つ。
最後の所有者が手放した実体を即消すと、上の決定の「公開済みリビジョンが参照する blob は
原則削除しない」を破る — 誰も所有していない blob を、公開済みの作品が参照している形は
普通に起こる (作った人が作品を消さずにアセットだけ手放した場合)。孤児の回収は参照
カウント + 猶予期間で 3-5 が受け持つ。

**手放せるかどうかの判断はまだ画面側にしか置けない。** 所有を手放すと、その sha256 を
指すマニフェストは次の保存で断られる (上の 3-2 の補足)。壊れるのは手放した瞬間ではなく
次に保存したときなので、気付ける形にならない。サーバは**どの作品がどの blob を使って
いるかをまだ知らない** (参照台帳は 3-5) ため、今開いている作品との突き合わせだけを
エディタが行い、使用中のアセットには削除の口を出さない。ほかの作品での使用は画面の
文言で断っている。3-5 で参照台帳が入ったら、この判断はサーバへ移せる。

## 補足 (2026-08-14 / Phase 3-5a)

参照台帳 (`blob_refs`) を入れるにあたって決めたこと。

**参照の主体は作品ではなく、R2 にあるリビジョンスナップショット。** 台帳のキーは
`(gist_id, revision, sha256)` で、`sketch_id` は持たない。守りたいのは「公開済みの
リビジョンが参照する blob」で、それが実際に配られる経路は D1 のポインタ →
R2 の `gists/{gistId}/{revision}.json` (ADR 0011)。配られる実体と同じ単位で数えないと
台帳と現実がずれる。`sketches` 側で数えると、Gist を切り離した作品 (`detachGist` は
`current_revision` を落とすが R2 のオブジェクトは残す) の過去リビジョンが台帳から
消え、まだ配られうる blob を孤児と誤判定する。

**記録は「R2 へ書いた」ところに寄せる。** R2 へリビジョンを書く経路は保存・取り込み
(`publishRevision`) だけでなく、閲覧時の埋め合わせと再検証 (`delivery.ts` の
`fill` / `revalidate` — 作者が GitHub 側で直接編集した分) もある。3 つとも
`storeRevision` を通す。どれか一つでも素通りすると、**配られているのに台帳に無い**
blob ができ、回収がそれを孤児と見なす。

**`blobs(sha256)` への外部キーは張らない。** マニフェストは利用者が書けるので、実体の
無い sha256 も書ける。外部キーがあるとその保存で参照の記録だけが失敗し、配信の
ポインタが進まなくなる。宙に浮いた行は、回収が `blobs` を起点に引く限り無害。

**読めないマニフェストは「参照していない」と数える。** 壊れた一覧は実行時の名前解決も
通らない (`assetUrlsForFiles` が同じ `readAssetManifest` で読めずに諦める)。配られない
ものを守ると、回収されるべき実体が永久に残る。保存経路が壊れたマニフェストを断るのとは
役割が違う — あちらは利用者に直させる、こちらは既に外にあるものをどう数えるか。

**同じ台帳を 2 つの読み方で使う。**

| 用途 | 読む範囲 | 理由 |
|---|---|---|
| 手放し (`DELETE /api/assets/<sha256>`) | 今配信しているリビジョンだけ | |
| 回収 (3-5b の GC) | 全期間 | 過去リビジョンは R2 に残り、いつでも配りうる |

手放しが今の断面しか見ないのは、**所有を手放しても配信中の作品は壊れない**ため
(実体は残り、配信 `/a/<sha256>/<name>` は D1 を引かない)。実際に壊れるのは次の保存で
マニフェストが断られるところだけ (3-2 の補足) なので、判断の基準は「次に保存される
中身」= 今のリビジョンに限られる。過去まで数えると、一度でも使った実体は作品から
外した後も永久に手放せず、クォータが空かなくなる。

**他人の作品は数えない。** 同じ中身を別の人が持ち込んでいれば相手の `user_blobs` にも
行があり、こちらが手放しても相手の参照は生きたまま。他人の使用を理由に自分のクォータを
縛るのは筋が違う。

## 補足 (2026-08-14 / Phase 3-5b)

**孤児の回収が入った。詳細は ADR 0015。** 上の決定の「GC は参照カウント + 猶予期間で、
公開済みリビジョンが参照する blob は原則削除しない」を実装した側で、決めたことは 4 つ。

- 走らせるのは Cron。載せる器として、アダプタのエントリを包む自前の `worker.ts` を置いた
- 孤児は「所有が無く、**全期間**のどのリビジョンからも参照されていない blob」
- 猶予は `blobs.created_at` ではなく**孤児と気付いた時刻** (`orphaned_at`) から数える。
  上げた直後の blob は所有があるので孤児ではなく、孤児になるのは手放した瞬間
- 消す順は R2 → D1。逆にすると台帳から消えて実体だけが残り、二度と見つけられない

**dedup は実体を確かめてから省く。** 3-1 は「既にある blob なら転送をスキップする」と
だけ決めていたが、回収が R2 → D1 の順で消すため「台帳にあるのに実体が無い」窓ができる。
その間に転送を省くと、**中身だけ存在しないアセット**を持つ作品が生まれる。claim
(`POST /api/assets`) は台帳で見つけた blob を R2 に照会してから `stored` と答える。

これで 3-4b の申し送り (「手放してよいかの判断はまだ画面側にしかない」) は閉じた。
エディタの突き合わせ (今開いている作品) は先回りの案内として残し、断りの最終判断は
サーバが台帳を見て行う (409 `asset_in_use`)。**別のタブで開いた別の作品**は画面からは
見えないので、この二段構えが要る。

## 補足 (2026-08-14 / Phase 3-6)

**p5 を実際に通す E2E を足した** (`e2e/asset-sketch.spec.ts`)。3-3 までのアセット系
E2E は、受け口・配信・素の `<img src>` / `new Image()` への代入までしか踏んでおらず、
`loadImage` / `loadModel` は一度も呼ばれていなかった。実行時解決 (ADR 0014) は
**p5 の実装を読んだ上で**組んであるので、その前提が崩れたことは p5 を通さないと
分からない。

**確認は画素で行う。** 「読めた」ではなく「正しい中身が正しい向きで描かれた」まで
見るために、種の PNG は 2x1 で左が赤・右が青にしてある。canvas から画素を読めること
自体が、配信の `Access-Control-Allow-Origin: *` が効いていることの確認にもなる
(taint された canvas は読めない)。

**踏んで分かったこと**: p5 の OBJ パーサは `vn` を持たないファイルに**法線を計算せず、
零ベクトルのまま残す**。`normalMaterial()` を当てると面が真っ黒になり、「モデルが
読めていない」のと区別が付かない。テスト側は `fill()` で色を置いている。

**過去リビジョン再現**は `asset-gc.spec.ts` が blob 側で見ている (「一度でも保存した
作品が使った実体は、外して手放した後も残る」)。旧リビジョンを描き直す UI は Phase 4 の
リビジョン履歴なので、そこで画面側の確認が要る。

## 補足 (2026-08-14 / #65)

**所有の検査は「保存経路」の規則ではなく、外の中身を配信に載せるすべての口の規則だった。**
3-2 の補足は「保存経路 (`PUT /api/sketches/:id/files`) で `user_blobs` に照会して断る」と
書いたが、取り込み (adopt — ADR 0012) は同じ中身を保存を経ずに `publishRevision` まで
運ぶのに、検査が無かった。配信 `/a/<sha256>/<name>` は D1 を引かないので、他人の作品の
`assets.json` から sha256 を書き写した Gist を取り込むと、**クォータを一切使わずに
アセット付きの作品が実際に配られていた** (#65)。取り込みにも同じ検査を通した。

**自動で計上する案 (取り込み時に claim) は採らない。** 「他人の blob を自分のものとして
計上する」形になり、上で決めた計上規則と衝突する。他人のアセットを持ち込む道は
フォーク (#44 / Phase 4) で、あちらは GitHub 側の blob 共有と `Forked from` を伴う。
adopt には出所を示すものが何も無く、計上だけが増えることになる。

**所有を手放した後は取り込みでも断られる。** 3-4b の補足の「手放すと、その sha256 を
指すマニフェストは次の保存で断られる」に、次の**取り込み**も加わる。

**まだ残っている口**: 配信の `fill` / `revalidate` (`lib/sketches/delivery.ts`) は、
作者が GitHub 側で直接書き換えた `assets.json` を閲覧のたびに拾って R2 と参照台帳に
載せる。3-5a の補足が「断る機会の無いまま壊れた形が入ってくることはある」と書いた
経路そのもので、こちらは**利用者の要求を断る**話ではなく背景処理の扱いなので、
断り方 (配信を止めるか / そのアセットだけ落とすか / 作者に知らせるか) の設計が別途要る。
