# 0002: 作品の正本を作者自身の GitHub Gist に置く (D1 ハイブリッド)

## 状態

採用 (2026-08-11)

## 文脈

差別化要件に「Gist/GitHub 連携」「バージョン管理」がある。Gist はリビジョン履歴を標準で持ち、
canvastage が既に「実行のたびに debounce PATCH → リビジョン化」を実装済み。
規約調査 (Issue #1 参照) の結論は「ユーザー自身のアカウントに OAuth で保存する形を禁止する
条項は無い。ただし条件付き」。同構成の先例として bl.ocks.org が約 10 年運用された。
一方、全体ギャラリー・検索・公開範囲・統計は Gist だけでは表現できない。

## 決定

- 作品のコードと assets.json は**作者自身の公開/secret Gist を正本**とする (OAuth scope=gist)
- メタデータ (タイトル・タグ・公開範囲・統計) とアセット台帳は D1 に持つ
- 閲覧配信は自前キャッシュ (R2/KV) から行い、キャッシュは GitHub 障害時のレプリカを兼ねる
- 規約上の成立条件を運用要件とする:
  1. 閲覧者トラフィックを GitHub (API/raw) に直接流さない
  2. 書き込みは各ユーザー自身のトークンで、レート制限を遵守する
  3. 未認証アクセスに依存しない
- 公開範囲は public = 公開 Gist、限定公開 = secret gist (private ではない旨を明示)。
  真の非公開は要件から除外した
- 更新検出: webhook が無いため、自サービス経由の更新はエディタがバックエンドへ通知し、
  外部編集・削除は表示時の conditional GET (ETag) と 404 tombstone で拾う

## 影響

- 作品データはユーザーの所有物のまま (エクスポート経路が構造的に存在し、ロックイン無し)
- Gist の制約 (テキストのみ・フラット・1MB/file) がスケッチ形式の制約になる → ADR 0003
- GitHub は裁量で API を停止できるため、キャッシュ = レプリカの維持が可用性要件になる
- gist scope が全 Gist 書き込み権限である旨をログイン時に明示する義務を負う
