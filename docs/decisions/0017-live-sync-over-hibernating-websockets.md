# 0017: 準リアルタイム同期は「状態を持たない Durable Object」と hibernate する WebSocket で配る

## 状態

採用 (2026-08-15)

## 文脈

要件 3.4 の共有体験 — 「作者がライブコーディングし、閲覧者が数秒遅れで追従できる」。
Phase 4 の完了条件そのもので、p5stage の差別化の中核にあたる。

配る土台は揃っていた。ADR 0011 が閲覧経路から GitHub を外し (D1 のポインタ → R2 の
不変オブジェクト)、ADR 0016 (4-1) が**今のポインタ以外の版を出す道**を開いた。
足りないのは「版が進んだことを、開いている閲覧者へ伝える経路」だけ。

ADR 0001 は「準リアルタイム同期の配信は Durable Objects」と決めていたが、**その中で
どう配るか**は決めていない。4-1 は引き継ぎとして 3 つ残した — 進行点が 3 か所に
散っていること、中身だけを返す口が無いこと、`SketchView` が `PreviewHost` を
保持していないこと。

決めることは 5 つある。

1. **通知経路。** SSE か WebSocket かポーリングか
2. **Durable Object が何を持ち、何を配るか**
3. **「版が進んだ」をどこから言うか**
4. **誰に購読を開くか** (限定公開の扱い)
5. **上限をどこに置き、超えたら何が起きるか**

## 決定

### 1. 経路は Hibernation WebSocket — SSE を退けたのは課金の構造

最初に書いたのは **SSE** だった。流すのは「新しい版が出た」だけで閲覧者から送るものは
無いので単方向で足り、`EventSource` は再接続を組み込みで持ち、HTTP なので既存の
Astro のルート・`middleware.ts` の顔の振り分け・キャッシュヘッダの作法にそのまま乗る。
実装は最も小さい。**課金を数えたら成立しなかったので変えた。**

Durable Objects の枠 (Workers Free plan) は requests 100,000/日 と duration
13,000 GB-s/日。duration は実際の使用量ではなく **128 MB 固定**で課金されるので
1 秒 = 0.128 GB-s、つまり枠の実質は「DO が起きている時間 28 時間/日」。

- **SSE は hibernate できない。** 応答ストリームが開いている限り「処理中のリクエスト」に
  当たり、DO はメモリに留まる (Cloudflare の docs も「`accept()` した WebSocket は
  接続している間ずっと duration 課金」と明示している)。**1 つの作品に 1 人が 24 時間
  繋ぎっぱなしにするだけで 86,400 秒 × 0.128 = 11,059 GB-s/日 = 無料枠の 85%**。
  作品 1 件で終わる
- **Hibernation WebSocket は繋いでいる時間が課金されない。** 課金は
  `webSocketMessage` 等を処理している時間だけ。**送信 (outgoing) メッセージは無料**、
  受信は 20:1 で request 換算、`setWebSocketAutoResponse()` の ping/pong は
  wall-clock を消費しないので duration にも乗らない。publish 1 回を 30ms と見ても、
  無料枠の中に 1 日 300 万回以上入る
- **ポーリングは限定公開で効かない。** 公開作品なら `s-maxage` でエッジに逃がせるが、
  限定公開は `private, no-store` (ADR 0011) なのでキャッシュが効かず、閲覧者数 ×
  ポーリング頻度がそのまま Workers の request 枠を削る。**ライブコーディングこそ
  限定公開で使われる**場面なので、いちばん効かせたいところで効かない

結果として、同期機能そのものの費用はほぼゼロになり、**Free plan で先に尽きるのは
DO ではなく Workers の 100,000 requests/日** (ページ表示・API・アセット配信) になる。

`EventSource` の再接続を手放した分は、`live-client.ts` が指数バックオフ + ジッタで持つ。

### 2. Durable Object は状態を持たない中継器で、配るのはリビジョン SHA だけ

粒度は作品 1 件 = DO 1 つ (`idFromName(sketchId)`)。

**hibernate から戻ると constructor が再実行され、インスタンス変数は消える。**
これは制約であると同時に設計の指針で、`SketchChannel` には購読者の集合も
「最後に流した版」も持たせない。

- 購読者は `ctx.getWebSockets()` が hibernate をまたいで返す
- 再接続の間に進んだ版は、**クライアントが繋ぎ直した直後に現在の版を 1 回引いて**
  埋める (`GET /api/sketches/:id/head`)。DO に覚えさせるより、既に真実を持っている
  D1 に聞く方が確かで、hibernate の制約とも噛み合う

**中身ごと push しない。** 配る道は既にあり (D1 のポインタ → R2 の不変オブジェクト)、
4-1 が作った過去の版の解決をそのまま使える。DO に他者のコードを溜める理由が無く、
閲覧側は追従でも通常の閲覧でも同じ経路から中身を受け取ることになる。中身を返す口
(`GET /api/sketches/:id/revisions/:rev`) は 4-1 が「必要になる次の縦切りで作る」と
予告した分で、`resolveRevisionContent` を通すので**台帳と R2 だけで閉じ、GitHub へは
行かない**。

`ctx.storage` も使わない。SQLite backend を宣言しているのは、Workers Free plan で
使える Durable Objects が SQLite backend のものに限られるため。

### 3. 進行点は `publishRevision` の 1 つに寄せる

4-1 の時点では、保存・取り込みが `publishRevision` を通る一方、閲覧時の埋め合わせと
再検証 (`delivery.ts` の `fill` / `revalidate`) は `storeRevision` +
`setCurrentRevision` を自分で並べていた。**散ったまま知らせを足すと知らせも 3 か所に
散り、どれか一つを書き忘れた経路だけ静かに追従しなくなる。**

`publishRevision` に `etag` 引数を足して一般化し、4 経路すべてをそこへ通した。

寄せるにあたって**失敗の扱いが違っていた**ので、握り潰す側に揃えた。`fill` は
`storeRevision` の失敗を例外として上げ、`resolveSketchContent` の catch が
`unavailable` に化けさせていたが、そのとき中身は手元にある — **配れるのに配らない**形に
なっていた。写しを残せなかっただけなら、その閲覧を失敗にする理由が無い。

知らせは `waitUntil` に預けて待たない。正本にも R2 にも既に書けているので、届いたか
どうかは保存の成否と関係が無く、**取りこぼしても再接続時の追いつきで回復する**。

### 4. 購読の鍵は sketchId — 作品ページを開ける条件と同じ

`unlisted` は「URL を知る人は誰でも見られる」という約束 (要件 3.4) なので、購読の
入口にだけ別の強度を要求しても守るものが増えない。ログインは要らない。

代わりに `Origin` は確かめる (ADR 0008 の `rejectForeignOrigin` を通す)。読み取りしか
しない口だが、**他サイトに埋め込まれたページから購読されると Durable Object が起きる** —
状態は変わらなくても費用は動く。存在しない作品にもチャネルを開かない (当てずっぽうの
ID を並べるだけで DO をいくつでも作れてしまう)。

公開範囲で差を付けるのは、中身を返す口のキャッシュだけ。公開作品は
`public, max-age=31536000, immutable` (不変なのは中身そのもので、作品ページの HTML と
違って作者名もタイトルも入らない — ADR 0016 で分けた話の続き)、限定公開は
`private, no-store`。購読そのものは HTTP のキャッシュに乗らない。

### 5. 上限は作品あたり 1000 接続。超えても閲覧は壊さない

1 つの作品がバズったときの挙動を、Cloudflare 側の限界に当たる前にこちらで決めておく。
超えた場合も**作品ページは普通に見えて、追従だけしない**。

断り方は 503 ではなく **101 を返した直後の close code (4001)**。ブラウザからは
upgrade のステータスが読めないので、503 だとクライアントは混雑と障害を区別できず、
繋ぎ直しを投げ続ける (それ自体が要求数を食う)。close code なら読めるので、
混雑と分かった時点で繋ぎ直しをやめられる。

## 影響

- `apps/web` に Durable Object のバインディングが増えた (`SKETCH_CHANNEL` /
  `new_sqlite_classes`)。クラスは `worker.ts` から export する — アダプタの出力
  (`dist/server/entry.mjs`) にも `durable_objects` / `migrations` ごと引き継がれるので、
  E2E の細工 (`prepare-dev-worker.ts`) は増やさずに済んだ
- **デプロイの形が変わった。** DO クラスの作成・削除・改名は原子的な操作で段階的
  ロールアウトに載らないため、`wrangler deploy` でしか適用できない。PR プレビューが使う
  `wrangler versions upload` は code 10211 で拒否するので、**新しい DO を入れる PR は
  必ずプレビューを出せない** (main への deploy で適用され、以降は出る)。落とし続けると
  required check が詰まって適用の道に辿り着けないので、CI はこのコードに限って
  skip 扱いにする。見逃すのは 1 コードだけで、他のデプロイ失敗は今までどおり止める
- **この変更をまたぐロールバックはできない。** DO のライフサイクル変更より前の
  バージョンへは戻せなくなる (Cloudflare の制約)。同じ理由で、あちらは「ライフサイクル
  変更は他のコード変更と独立してデプロイする」ことを勧めている — 今回は 1 つ目の DO で
  戻す先の挙動も無いため同じ PR に入れたが、**2 つ目以降を足すときは分けて出す**
- 追従するのは**最新の版を、中身が出ている状態で見ているとき**だけ (`data-live`)。
  過去の版を開いた閲覧者を勝手に最新へ動かさない。中身が出ていない作品 (未保存・
  削除済み・取得不能) は差し替える先の DOM が無いので購読しない — 保存された後の姿は
  開き直せば出る
- **SHA には前後関係が無い。** 追いつき (`head`) の答えが遅れて着くと、その間に受けた
  新しい版を古い版で上書きしうるので、引き始めた時点から版が動いていたら答えを捨てる。
  知らせどうしの順序は DO からの送信順で保たれる
- 作品ページのコード表示は JS が組み直すようになった。Astro の scoped style は
  SSR が出した要素にしか印を付けないため、`.sketch-file` のスタイルは
  `styles/sketch-view.css` へ移した (`.sketch-tabs` が先に同じ理由でそこにある)
- 購読者が 0 の作品への知らせも DO を 1 回起こす。間引く仕掛けは入れない
  (1 保存 = 1 request で、枠に対して十分小さい)
- 生存確認は今のところクライアントから 45 秒ごとに送るだけで、**応答が返らないことは
  見張っていない**。切れたことはブラウザの close イベントで分かる前提に立っている。
  切断に気付けない環境が出てきたら、pong のタイムアウト監視を足す
- 課金の前提が変わる (hibernation の条件・無料枠) と設計の根拠ごと変わる。SSE へ
  戻す判断があるとすれば、**接続数ではなくメッセージ頻度が支配的になったとき**
