# 0023: 何に課金し、何に課金しないか

## 状態

採用 (2026-08-25) — **原則のみ。実装は行わない** (下記「決定 4」)

## 文脈

要件 4 節と roadmap の v2 に「有料プラン (クォータ拡大に加え、より良い付加価値)」が
挙がっているが、中身は未定のままだった。リポジトリを公開する (ADR 0022) にあたって、
**何に課金し、何に課金しないかを先に決めておく**。原則が無いまま Phase 3 のアセット
クォータを実装すると、後から課金を載せるときに設計が歪むためで、実装を急ぐ話ではない。

### 原価を数えると、ほとんど何もない

| 項目 | 原価 | 理由 |
|---|---|---|
| 転送 (egress) | ゼロ | Cloudflare の構造 (ADR 0001) |
| コード本体の保存 | ゼロ | 正本はユーザーの Gist (ADR 0002) |
| D1 | ほぼゼロ | 持つのはポインタとメタデータだけ (ADR 0011) |
| Durable Objects | ほぼゼロ | hibernation で接続時間が課金されない (ADR 0017) |
| Workers リクエスト | 定額の中でかなり伸びる | |
| **R2 (アセット実体)** | **ここだけが利用者数に比例** | ストレージ課金 |
| モデレーション | 人的コスト | 金ではなく時間 |

**実質的な変動費は R2 のストレージだけ**で、数百 GB を抱えても月に数ドルのオーダーに収まる。
ここから 2 つの帰結が出る。

1. **課金は生存条件ではない。** 利用者が増えても財布が痛まない構造になっている
2. **だから「原価を賄うための課金」という物語は使えない。** 月数ドルの原価に対して
   「サーバー代のために」は説得力がない。課金するなら別の根拠が要る

### ロックイン無しを掲げると、課金できるものが決まる

要件 5.3 が「サービス都合のロックインが構造的に無い」と言っている以上、**データを人質に
した課金は封じられる**。これは制約であると同時に、課金対象を選ぶ指針になる。

## 決定

### 1. 課金しないものを先に決める

以下は**永久に無料**とする。将来の自分への拘束としてここに書く。

- **エクスポート** — 有料にした瞬間、要件 5.3 のロックイン無しと正面衝突する。
  そもそも正本がユーザーの Gist にあるので、売り物にする資格がない
- **作品数・リビジョン履歴へのアクセス** — Gist 側に既に制約がある (要件 6 節) ものを
  二重に絞るのは人質に取るのと同じ
- **作品の非公開化** — secret gist で自分でできることを売るのは詐欺的

### 2. 収益経路は 2 つ

**GitHub Sponsors。** 公開して初めて成立する経路で (private リポジトリには支援できる
対象が存在しない)、決済と税務を GitHub が引き受ける。原価が月数ドルのオーダーである以上、
少額の支援でも十分に回る。このプロジェクトの性格 — 作りたいから作っていて、良いと思った
人が支える — と最も摩擦が少ない。

**アセット容量 (R2) のクォータ。** 唯一の実変動費に紐づくので、課金の正当性を説明しやすい。
Phase 3 で実装するクォータがそのまま土台になる。

### 3. 検討して採らなかった案

**ライブ同期の同時視聴者数。** 実原価に紐づく点は良いが、ADR 0017 の hibernation で
接続時間の課金は既に回避済みで、売るほどの原価が発生しない。作品あたり 1000 接続の上限は
**abuse 対策として残し、課金の対象にはしない**。

**教育向けクラス機能のセルフホスト版を商用ライセンスで販売。** 教育機関は最も課金しやすい
相手だが、ADR 0022 で CLA を取らないと決めたため、外部の貢献が入った後にデュアル
ライセンス化する道が事実上塞がっている。**自分のホスティング上の有料機能としてなら将来
やれる**ので、可能性そのものは閉じない。

**ブースト方式 (Discord のサーバーブースト型)。** 閲覧者が課金して特定の作品を
「ブースト」し、その作品の能力が上がる形。**採用しないが、噛み合う点が多いので将来の
出発点として記録する。**

噛み合う理由:

- 支払いが原価の発生点と一致する。ブーストで上がるのがアセット容量と同時接続なら、
  「払った分だけ原価が増える」が構造的に保証され、赤字が出ようがない
- 作者は無料のまま。作りたいから作っている人に金銭的障壁が生じない
- ロックイン無しと衝突しない。ブーストは**追加**であって剥奪ではない
- ファンが作品を支える形は OpenProcessing (作者が払うモデル) に無い差分になる

やるとしたら守るべき条件:

- **露出は絶対に売らない。** ブーストでギャラリーの順位が上がる設計にすると金で注目を
  買えることになり、コミュニティの信頼を一度で失う。売ってよいのは容量・同時接続・装飾まで
- **ブーストが切れても既存アセットを消さない。** 止まるのは新規アップロードだけ。
  要件 5.4 の「公開済みリビジョンが参照する blob は原則削除しない」が既に同じ答えを出している
- **収益を作者へ還元しない。** 還元するとプラットフォーム型送金になり、税務も実装も
  一気に重くなる。ブーストは「作品の能力が上がる」形で作者に還る、と整理する
- **ブースターは作品に対して何の権利も持たない。** 支援であって購入ではない旨を規約に書く

採らない理由は、下記 4 の決済の重さに尽きる。需要が見えてから改めて判断する。

### 4. 決済基盤の選択と課金の実装は保留する

日本で個人が継続課金を行うと、**特定商取引法により氏名と住所の表示義務**が生じる。
Merchant of Record (Paddle 等) を挟めば回避できるが手数料が上がる。そして原価が月数ドルの
オーダーである以上、**決済の実装・手数料・税務対応が原価を大きく上回る**。

したがって当面の収益経路は **GitHub Sponsors のみ**とし、クォータ課金とその決済基盤は
「ブーストしたい人・払いたい人が実在すると分かってから」決める。

## 影響

- Phase 3 のアセットクォータは、**将来の課金で引き上げられる余地を残した形**で実装する
  (上限をコードに焼き込まず、ユーザーごとの値として持てるようにしておく)
- 要件 4 節と roadmap の v2 の「有料プラン」は、この ADR を参照する形に改める
- Sponsors を有効化したら `.github/FUNDING.yml` を置く。**GitHub Sponsors だけを書き、
  クォータ課金を始めてもその決済基盤をここへ足さない** — FUNDING.yml が指すのは「支援」で
  あって、サービスの対価ではないため
- Sponsor ボタンの表示にはリポジトリ側の Sponsorships 設定 (Settings → General → Features)
  も要る。切り替えは REST の `PATCH /repos/{owner}/{repo}` では効かない (`has_sponsorships` は
  黙って無視される) が、GraphQL の `updateRepository(hasSponsorshipsEnabled:)` では変えられる。
  現状の確認は次で足りる:

  ```bash
  gh api graphql -f query='{ repository(owner:"shinyaoguri", name:"p5stage") {
    hasSponsorshipsEnabled fundingLinks { platform url } } }'
  ```

  `hasSponsorshipsEnabled` がリポジトリ設定、`fundingLinks` が GitHub 側の FUNDING.yml 解釈
  結果。後者が空ならボタンは出ない (公開ページの埋め込み JSON も `showSponsorButton: false`
  を返す)
- FUNDING.yml は `github: shinyaoguri` の 1 行だけに保ち、コメントを書き足さない。設計意図は
  この ADR に置く — GitHub 側の検出を疑うとき、ファイルが素であるほど切り分けが速い
- **FUNDING.yml を置いてから Sponsor ボタンが出るまで、数時間かかることがある** (#119)。
  新規リポジトリでは数秒で通ったので即時反映を前提にしてしまったが、このリポジトリでは
  ファイル・設定・Sponsors リスティングのすべてが正しい状態でも、反映まで半日近くかかった。
  出ないうちは設定を疑うより、**まず一日待つ** — その間に配置を変えたり設定をトグルしたりしても
  何も起きず、切り分けの手数だけが増える
- 課金を実装する段になったら、この ADR の状態を更新するか後継の ADR を起こす
