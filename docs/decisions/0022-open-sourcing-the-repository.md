# 0022: リポジトリを AGPL-3.0 で公開する

## 状態

採用 (2026-08-25)

## 文脈

きっかけは GitHub Actions の枠だった。private の Free 枠は 2,000 分/月で、CI は
1 PR あたり wall clock 約 10 分を 2 回 (PR と main への push) 走る。public リポジトリなら
GitHub-hosted の standard runner は無料になる。

**ただしこれを公開の理由にはしない。** 枠は self-hosted runner でも e2e の削減でも
追加購入でも解ける。対して公開は**片方向にしか動かない** — private から public はいつでも
できるが、public から private は fork とアーカイブが残るので取り消せない。戦術的な問題を
不可逆な決定の根拠にすると、後から理由が消えたときに決定だけが残る。

そこで公開自体の是非を論じた。

### 堀はコードにない

競合に置く OpenProcessing.org の参入障壁は、10 年分の作品とユーザーとギャラリーの賑わい
であって、ソースコードではない。仮にあちらのコードが明日全公開されても立場はほぼ揺らがない。
逆にこちらのコードが公開されても、誰かがクローンして立てた「作品ゼロのギャラリー」に
価値はない。

このジャンルの障壁は次のところにある。

- 作品とユーザーの集積 (ネットワーク効果)
- GitHub の規約と付き合う運用知 (要件 5.2 に書いてあるものを読むのと、運用して痛い目を
  見るのは別)
- モデレーションと abuse 対応の実運用
- ドメインとブランド

**コード秘匿が守っているものが何もないなら、秘匿のコストだけが残る。**

### 公開が主張と整合する

差別化の第一項は「作品データはユーザー自身の所有物のまま」で、要件 5.3 は
**サービス都合のロックインが構造的に無い**と言っている。これは機能ではなく信頼を売る設計で、
信頼を売るサービスがクローズドなのは主張として弱い。「あなたのデータはあなたのものです、
ただし我々が何をしているかは見せません」は、論理的には両立しても感情的には矛盾して聞こえる。
Gist を正本に据えた設計 (ADR 0002) の説得力は、コードが読めることで一段上がる。

加えて、**他者コードを実行するサービスである以上、セキュリティモデルは検証可能なほうが
強い**。ADR 0008 の別オリジン分離が本当に成立しているかを第三者が確かめられる。
「安全です」より「ここに書いてあります」のほうが強い主張になる。

対象ユーザーが p5.js コミュニティ = OSS 文化圏そのものであることも効く。p5.js は
Processing Foundation の OSS で、共有と fork が規範の界隈にいる。

### 今が最も安全なタイミング

Phase 1 の途中で、稼働しているサービスがまだ無い。攻撃対象が存在しない段階なら、
コードが読まれても実害がない。**Phase 5-6 まで進んでから公開するほうが、動いている
サービスの攻撃面を晒すことになる。**

abuse 対策の閾値が読まれる懸念は、roadmap の方針 (アセットの abuse は Phase 3 の時点で
allowlist / クォータを実装する) と噛み合う。現時点では閾値がまだ実装されていないので、
晒すものが存在しない。実装する時点で閾値を設定値へ逃がせばよく、公開のブロッカーには
ならない。

### 公開前スキャンの結果

ブロッカーは無いことを確認した。

- 履歴に `.env` / `.dev.vars` / 鍵ファイルの追加コミットは無い (あるのは
  `.dev.vars.example` 2 本で、中身はプレースホルダのみ)
- 追跡ファイル・Issue・PR の本文にトークン様の文字列、個人のメールアドレス、
  ローカルの絶対パスは無い
- `pull_request_target` は不使用。`pull_request` のみなので fork に secrets は渡らない
- プレビューデプロイは `head.repo.full_name == github.repository` で fork を除外済み
- 本番デプロイは `github.event_name == 'push' && github.ref == 'refs/heads/main'` 限定で、
  fork から本番に触れる経路が無い

## 決定

### 1. リポジトリを public にする

### 2. ライセンスは AGPL-3.0

改変してホスティングするなら改変部分も公開する義務が生じるので、**他人が丸ごとコピーして
SaaS を立てて課金することを法的に抑止できる**。著作権者である自分がホスティングして
課金するのは完全に自由 (ADR 0023)。OSS 文化圏でも受け入れられている。

退けた選択肢:

- **Apache-2.0 / MIT** — 採用と貢献は最大化されるが、丸ごと商用クローンを止められない。
  「使われること」を最優先するなら合理的だが、課金を視野に入れる以上こちらは取らない
- **BSL / Elastic License** — 抑止力は最強だが「OSS ではない」と見なされる。相手が
  p5.js 界隈である以上、反発のほうが大きい

### 3. CLA は取らない

外部コントリビューターから著作権譲渡や広範な利用許諾を取れば、将来デュアルライセンス
(セルフホスト版を商用ライセンスで販売する等) の余地が残る。**取らない。**

理由は、個人プロジェクトに CLA は重すぎるから。PR ごとの署名は敷居を上げ、OSS 文化圏では
敬遠されることもある。外部 PR が来ること自体が稀な段階で、敷居を上げて誰も来ないほうが
損失が大きい。

**代償を明記しておく。外部の PR を受け入れ始めると著作権が分散し、後からライセンスを
変更できなくなる。** 将来デュアルライセンス化したくなったら、その時点の貢献者全員に
個別に許諾を求めることになる (規模が小さいうちなら可能だが、大きくなれば不可能)。
これを承知の上での決定であり、後から「そんなつもりではなかった」とはしない。

### 4. 公開後も CI の構造は変えない

fork からの PR で壊れないことは既に設計に入っている (上記スキャン結果)。
Cloudflare の資格情報と Gyazo のトークンはどちらも「未設定なら黙ってスキップ」の
guard を持つので、secrets が渡らない fork PR でも `ci-gate` は緑になる。

## 影響

- **GitHub Actions が無料になる。** #108 で絞った e2e の実行条件を戻すかは別途検討する
- **AGPL 13 条の申し送り。** ネットワーク越しに利用させる以上、サービスの画面に
  ソースの入手経路を置く必要がある (ライセンス本文も「web application なら Source リンクを
  表示せよ」と例示している)。サイト共通のフッターは未実装なので、**Phase 5-6 で
  `apps/web/src/layouts/BaseLayout.astro` にフッターを作るときに GitHub へのリンクを含める**
- **秘密の扱いが後戻りできなくなる。** 以降、うっかり commit した秘密は即座に公開される。
  secret scanning と push protection を有効にして検知より予防に寄せる
- 貢献の入口として `CONTRIBUTING.md`、脆弱性の報告経路として `SECURITY.md` を置く。
  後者は他者コードを実行するサービスである以上、公開 Issue に書かれると困るため
- 課金の方針は ADR 0023 で別に定める
