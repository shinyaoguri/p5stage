# 0010: Gist の読み書きは Worker が代理し、公開範囲は最初の保存で固定する

## 状態

採用 (2026-08-12)

## 文脈

Phase 2-3 で「保存」を通す。正本は作者自身の Gist (ADR 0002)、トークンはサーバ側に
封じてある (ADR 0009)。Issue #34 が積み残していた設計判断がここで効いてくる。

- **Gist API を叩くのはクライアントか Worker か**。要件 5.2 の「閲覧者トラフィックを
  GitHub に直接流さない」はキャッシュ層の話だが、書き込み側をどちらに置くかは別問題
- Gist API には、スケッチ形式にそのまま跳ね返る制約がいくつかある。
  実装してみて分かったものを含め、ここで扱いを決めておかないと、
  「保存したのに次に開くと違う」が静かに起きる

## 決定

### 1. GitHub API は Worker が代理で叩く

読みも書きも `apps/web/src/lib/github/gist.ts` を通す。ブラウザから GitHub へは
一切出ない。ADR 0009 でトークンをサーバ側に封じた以上そもそも叩けないが、
判断としても Worker に寄せる。レート制限の遵守 (要件 5.2) を 1 か所で守れる。

読みも本人のトークンで行う。secret gist は URL を知っていれば匿名でも読めるものの、
匿名の制限は IP ごと 60 回/時で、**Workers の出口 IP は多数の利用者で共有される**。
認証付きなら利用者ごと 5000 回/時になる。閲覧者 (非所有者) への配信はこの口を使わず、
キャッシュ層 (Phase 2-5) が受け持つ。

### 2. 公開範囲は最初の保存で固定する

GitHub の Gist は**作成後に public / secret を変更できない**。D1 の `visibility` だけを
書き換えると、「限定公開にしたつもりが Gist は公開のまま」という嘘になる。

- 公開範囲は**エディタの設定で決める** (`defaultVisibility`。既定は公開)。保存ボタンは
  その通りに作り、押した後に尋ねない
- Gist が紐付いた作品の `visibility` 変更は **409 で断る**
- 変えたいときは別の作品として作り直す。移す口は Phase 2-6 (detach) で扱う

初回保存のダイアログで選ばせる形から改めた (#87 の段階 5)。エディタは**大勢の前へ
投影されながら書かれる場所**でもあり、保存のたびに画面いっぱいの尋ねる面が出るのは
その場面で最も邪魔になる。公開範囲は作るたびに考え直すものではなく「自分の既定」で
足りるので、決める場所を設定へ移した。**尋ねない代わりに、何として作られたかは
初回の保存でトーストが言う** (公開範囲だけは後から変えられないので、違っていたときに
早く気付けるほど作り直しが軽い)。

サーバ側の既定 (`normalizeVisibility`) は**限定公開のまま**変えない。あちらが守るのは
「指定漏れが黙って公開に倒れない」ことで、画面で明示的に選ばれた既定とは別の話。

### 3. 空ファイルは保存できない

Gist API は中身が空・空白だけのファイルを 422 で拒む。送ってから失敗すると、
その保存要求ごと落ちて**他のファイルの変更まで書けなくなる**。手前で弾き、
どのファイルが問題かを見せる。黙って落とす案は採らない (「保存したのに次に開くと無い」)。

### 4. 消えたファイルは明示的に削除する

PATCH は**送らなかったファイルをそのまま残す**。差分を作るために、更新前に一度 Gist を
読んで今あるファイル名を取り、消えたものを `null` で送る。往復は増えるが、
これを省くとエディタで消したファイルが Gist に残り、次に開いたときに甦る。
条件付き GET (ETag) で往復を省くのは Phase 2-5 のキャッシュ層の担当。

ただし**中身を読めなかったファイル (1MB 超で truncated) は差分の対象から外す**。
エディタはその中身を受け取っていないので、差分を取ると「消えたファイル」に見え、
次の保存で GitHub 側の大きなファイルを消してしまう。

### 5. 自動保存は Gist ができてから

初回だけは明示の「保存」でしか作らない。利用者の GitHub アカウントに物を作る操作を、
本人の意思なしに起こさないため。2 回目以降は**実行のたびに**間引いて PATCH する
(要件 3.2)。打鍵ごとではなく実行ごとにするのは、リビジョンが「動かした形」の履歴に
なるため。canvastage も同じ起点を採っている。

### 6. 作品名は description に置く。タイトル用のファイルは作らない

canvastage は一覧のタイトルを作るために `_名前.md` を Gist に足していたが、
持ち込まない。**利用者が書いていないファイルがスケッチに混ざる**うえ、
p5stage は作品名を D1 に持っていて Gist から復元する必要が無い。

## 影響

- Gist を触る処理はすべて `/api/sketches/:id/files` を経由する。クライアントは
  自分のオリジンしか知らない
- 保存 1 回につき GitHub API を 1〜2 回叩く (更新は読み + PATCH)。認証付き 5000 回/時に対して
  十分な余裕があるが、2-5 の条件付き GET で減らす余地として残る
- **公開範囲を後から変えられない**ことを画面で先に伝える義務が生じる (初回ダイアログ)
- 保存の途中経過 (器はできたが Gist はまだ) が状態として存在する。`gist_id` が NULL の
  作品はそれで、エラーではない
- タイトルを変えても Gist の description は次の保存まで古いまま。作品ページ (2-4) が
  見せるのは D1 のタイトルなので、利用者から見える不整合にはならない
