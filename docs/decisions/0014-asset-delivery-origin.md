# 0014: アセットは 3 つ目のオリジンから配り、実行時は配信 URL を直接参照する

## 状態

採用 (2026-08-14)

## 文脈

ADR 0003 で決めたアセット (R2 の不変 blob + Gist 内の assets.json) を、Phase 3-1 で
受け取り、3-2 で作品に結び付けた。残っているのは**ブラウザまで届ける経路**で、
ここには 3-1 / 3-2 の時点では決められなかった判断が 2 つある。

1 つは配信オリジンの作り方。ADR 0003 は「R2 + カスタムドメイン (本体と別オリジン)」と
だけ書いていて、ヘッダを誰が付けるかを決めていない。もう 1 つは実行時の解決先で、
ADR 0003 は「blob URL へ解決する」と書いているが、これは**実行 iframe を別オリジンに
置く前 (ADR 0007 より前)** の記述で、当時は「本体が持っている中身を iframe へ渡す」
形しか想定していなかった。

## 決定

### 配信は本体 Worker の 2 つ目のホスト (`assets.p5stage.org`) が受け持つ

`/a/<sha256>/<ファイル名>` で配る。引く鍵は sha256 だけで、ファイル名は無視する
(後述)。ホストが違えばブラウザから見て別オリジンなので、隔離はこれで成立する。

- **R2 のカスタムドメイン直結は採らない。** 安いが、`nosniff` も CORS も
  Transform Rules (コード外) で付けることになり、要件 5.1 の守りがリポジトリから
  読めなくなる。「他者のアップロードしたものをどう配っているか」はコードで残す
- **専用 Worker も採らない。** 隔離はホスト名で成立するので、デプロイ単位を増やしても
  得るものが無い。R2 のバインディング (`BLOBS`) も台帳 (D1) も既に本体にある
- **実行オリジン (preview) への間借りも採らない。** 同一オリジンになるので CORS が
  要らなくなる利点はあるが、**他者コードが走る場所に正本を同居させない**。実行
  オリジンで何かが破れたとき (ランナーの XSS、Storage 経由の細工) に、配信まで
  巻き込まれる形にはしない

セッション cookie は `__Host-` プレフィックス付き (ADR 0008) なので、同じ Worker に
載せても**この 2 つ目のホストには構造的に届かない**。アセットの配信に認証は無く、
sha256 を知っていれば誰でも取れる — マニフェストは公開作品の Gist に載るので、
実質公開のものを配っている。限定公開の作品でも同じで、「URL を知っていれば見られる」
という限定公開の性質と揃う。

本体のホストでは `/a/` を出さず、アセットのホストでは `/a/` 以外を出さない
(middleware)。同じ Worker が 2 つの顔を持つので、**どちらの顔で何を出すかは
コードで固定する**。

### 実行時はランナーで blob URL を作らず、配信 URL を直接参照する

ADR 0003 の「blob URL へ解決する」を、この点だけ差し替える。

- 大きいアセット (3D モデル・音声) を毎回メモリに載せずに済む
- `Range` が効くので音声のシークが動く
- `immutable` のキャッシュがブラウザに効き、エディタで実行し直すたびに取り直さない

代償は CORS で、配信は `Access-Control-Allow-Origin: *` を返す。認証を伴わない
公開 blob なので `*` でよい (cookie は届かず、返すものは誰でも取れる)。

### マニフェストを URL の表に変えるのは本体、ランナーは表を引くだけ

`run` メッセージに `assets` (ファイル名 → 絶対 URL) を載せて渡す (プロトコル 2)。
ランナーはマニフェストも配信オリジンも知らない。

- 実行環境に設定値を 1 つも増やさない。preview Worker が知っているのは本体オリジン
  だけという状態を保つ (ADR 0007)
- エディタと作品ページが**同じ解決**を通る。マニフェストの読み方が 2 つに割れない
- 受け取る側は `http(s)` の絶対 URL だけを受け付ける。本体は信頼する相手だが、
  信頼境界の作法 (中身をパーサに通す) は変えない

### 配信 URL に元のファイル名を残す

p5 の `loadModel` は `path.slice(-4)` で形式を判定する (実測)。`/a/<sha256>` だけの
URL では 3D モデルが読めず、Phase 3 の完了条件を満たせない。名前は URL の見た目と
拡張子のためだけにあり、**引くのは sha256 だけ**。同じ blob が複数の名前で参照
されれば URL も複数になるが、中身が同じなら実体は 1 つのままで、キャッシュが分かれる
以上の害は無い。

### 名前の解決は fetch / XHR だけでは足りない

p5 1.x の `loadImage` は、GIF を見分けるために一度 `fetch(path)` した後、GIF で
なければ **`img.src = path` に元のパスをそのまま渡す** (CDN の実体で確認)。既存の
`fileLoaderBridgeScript` (fetch / XMLHttpRequest の差し替え) はここに届かない。
`HTMLImageElement` / メディア要素の `src` と `setAttribute` も同じ表で解決する。

## 影響

- オリジンが 3 つになる (本体 / 実行 / アセット)。`resolveOrigins` は 3 つが互いに
  別であることを検証する。設定が欠けていれば起動時に落ちる
- アセットのホストでも Astro の静的ファイル (`/_astro/*`) は配信される。Workers の
  静的アセットは Worker より前で解決されるため。公開されている物ばかりで cookie も
  届かないので実害は無いが、「アセットのホストは blob しか出さない」とは言えない
- 配信は R2 だけで完結する (D1 を引かない)。台帳から消えたが R2 に残っている blob は
  配られ続けるが、実体を消すのは GC (3-5) の仕事なので、そちらで揃う
- `img.src` を読み返すと配信 URL が返る。p5 の読み込み失敗メッセージにも元のファイル名
  ではなく配信 URL が出る
- プロトコルを 2 へ上げる。本体とランナーは別々にデプロイされるので、片方だけ古い間は
  エディタが「プロトコルが一致しません」と言って止まる。黙ってアセットだけ解決
  されない状態より、理由が出て止まる方を採る
