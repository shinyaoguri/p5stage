# 0020: 検索は D1 の FTS5 (trigram) で引き、索引はトリガーで同期する

## 状態

採用 (2026-08-15)

## 文脈

Phase 5 の「発見」は、新着一覧 (「今」)・ユーザーページ (「誰」)・タグ
(「何について」) の 3 本まで入った。残る 1 本が**言葉から引く**道で、要件 3.5 の
「検索 (D1)」にあたる。

材料は D1 にあるメタデータだけ。**コードの中身は探せない** — 正本は作者の Gist で、
D1 には無い (ADR 0002)。閲覧経路に R2 は入れない (一覧は D1 だけで組む) ので、
索引に載せられるのはタイトル・説明・タグの 3 つになる。

制約が 2 つある。

- **利用者の半分は日本語で主題を書く。** タグで日本語を通した (Phase 5 のタグ) のと
  同じ理由で、検索も日本語で引けないと道として成立しない
- **打った字がそのまま SQL の式になる。** 検索は入力を式に直す唯一の機能で、
  他の入口 (タグ・タイトル) のように「正規化して弾く」だけでは足りない

## 決定

### 1. LIKE の全表走査ではなく FTS5 の索引を置く

`WHERE title LIKE '%語%'` は先頭にワイルドカードが付くので B-tree の索引が効かず、
毎回の検索が全表走査になる。D1 は読んだ行数で課金するため、**作品が増えるほど
1 回の検索が高くつく**。Cloudflare 自身の指針も、任意の部分一致には FTS5 の trigram
tokenizer を挙げている。

索引は `sketch_search` (fts5) 1 つ。列はタイトル・説明・タグと、作品へ戻るための
`sketch_id` (UNINDEXED — ID の断片が検索語に当たっても利用者にとって意味のある
一致ではない)。

### 2. tokenizer は trigram — 日本語のためにこれしかない

既定の unicode61 は**空白で語を割る**。日本語の文には空白が無いので、
「波の実験をするスケッチ」が丸ごと 1 語になり、部分一致がまったく効かない。
形態素解析器は D1 (workerd の SQLite) に持ち込めない。

trigram は 3 文字の窓で索引を作るので、語の切れ目を知らなくても引ける。
代償は 2 つあり、どちらも受け入れる。

- **2 文字以下の語では引けない。** 「猫」「波」のような短い日本語は索引に無い。
  0 件と答えると打ち方の問題が「そんな作品は無い」に化けるので、
  `lib/sketches/search.ts` が引く前に足切りし、3 文字以上で探すよう案内する
- **索引が太る。** 1 文書あたりの trigram は文字数とほぼ同じ数になる。探せるのが
  短いメタデータ 3 つだけなので、この規模では見合う

### 3. MATCH 式は 1 か所で組む — 語ごとに引用符で包む

FTS5 の MATCH は `AND` / `OR` / `NEAR` / `*` / `^` / `:` を構文として読む。
生の入力を渡すと `cat OR dog` が演算子として効き、`"` 1 つで SQL が構文エラーで
落ちる。**空白で割った語を 1 つずつ `"…"` で包み** (中の `"` は `""`)、並べて暗黙の
AND にする。組み立ては `lib/sketches/search.ts` だけが持ち、`store.ts` は
組み立て済みの式しか受けない (タグの正規化を `tags.ts` 1 か所に置いたのと同じ形)。

### 4. 索引の同期はトリガーで持つ

作品に触る口は既に多い — 作成・取り込み・フォーク・更新・タグの付け替え・切り離し。
アプリ側から `reindex()` を呼ぶ形にすると、**1 つ呼び忘れただけで「保存したのに
検索に出ない」**が起き、しかも気付きにくい。所有の確認を SQL の中でやっているのと
同じ理由で、同期も D1 の中に置く (`sketches` の insert / update of title,description /
delete と、`sketch_tags` の insert / delete)。

E2E は索引を種で蒔かない。`sketches` へ入れればトリガーが載せるので、**索引を別に
蒔く道があると、同期が壊れていても種のおかげで緑になる**。

### 5. 並びは関連度ではなく更新順

FTS5 は `rank` (bm25) を持つが、trigram の索引が数えているのは「3 文字の窓の
出現数」なので、それで並べても利用者に説明できる順序にならない。他の一覧
(新着・タグ・ユーザー) と同じ `updated_at DESC` に揃える。関連度で並べるなら、
まず何を関連とみなすか (題の一致を説明より重く見るなど) を決める必要がある。

### 6. 公開範囲は索引に持たせない

索引には限定公開の作品も入る。絞りは検索時に `sketches.visibility` 側でやる
(`listPublicSketches` と同じ条件 — 公開・書き出し済み・tombstone でない)。
公開範囲を変えるたびに索引を書き直さずに済み、`visibility` は検索語ではないので
索引に置く意味も無い。

## 帰結

- 日本語でも英語でも 3 文字以上なら部分一致で引ける。タグに無い言葉でも、
  題と説明に書かれていれば辿り着ける
- **2 文字の語は引けない。** 短い日本語の主題 (「波」「森」) は、タグを付けて
  `/tags/<tag>` で辿るのが今の答え。ここを埋めるなら別の索引が要る (2-gram を
  併せ持つ・語彙を持つ) ので、必要になってから決める
- 索引の分だけ D1 の書き込みが増える。作品の保存 1 回につき FTS5 の更新が 1 回
- 検索結果ページは `noindex`。クエリの数だけ URL が増えるので、検索エンジンに
  近似重複を見せない (`?rev=` を正典から外したのと同じ考え方 — ADR 0016)
- **`sketch_search` に別名を付けられない。** MATCH の左辺に取れるのは表の名前だけで、
  別名を書くと `no such column` になる (他の一覧が `s` を使っているのに揃えたく
  なるが、ここだけは書けない)
